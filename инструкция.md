# AI-генератор квизов — техническое задание

## 0. Роль

Ты — ведущий архитектор и разработчик продукта.

Твоя задача — не просто написать код, а спроектировать и реализовать надёжную систему генерации качественных обучающих квизов на основе нормативной/справочной документации.

Работай как команда из:

* архитектора ПО;
* AI/LLM-инженера;
* специалиста по RAG;
* специалиста по качеству генерации;
* UX-инженера;
* backend-разработчика;
* frontend-разработчика;
* тестировщика.

Но не создавай ненужную сложность.

Главный принцип:

> Максимальное качество при минимальном количестве AI-вызовов, разумной стоимости и малом времени генерации.

---

# 1. Цель продукта

Уже существует сайт-конструктор квизов.

Сейчас куратор создаёт вопросы вручную.

Нужно интегрировать в него AI-модуль, который позволит куратору:

1. выбрать раздел документации;
2. указать количество вопросов;
3. запустить генерацию;
4. получить пачку готовых квизовых вопросов;
5. быстро проверить их;
6. изменить/удалить отдельные вопросы;
7. добавить выбранные вопросы в существующий квиз.

Цель:

> максимально автоматизировать создание квизов и минимизировать время куратора.

Куратор не должен вручную писать вопросы, искать правильные ответы и искать подтверждение в документации.

---

# 2. Главный принцип продукта

Это НЕ генератор экзаменационных вопросов.

Это НЕ система, которая просто перефразирует документацию.

Это НЕ:

```
документация → LLM → вопрос
```

Нужен:

```
документация
    ↓
понимание знаний и правил
    ↓
структурированное представление предметной области
    ↓
планирование покрытия
    ↓
создание интересных ситуаций
    ↓
квизовые вопросы
    ↓
проверка по источнику
    ↓
точечное исправление
    ↓
куратор
    ↓
готовый квиз
```

---

# 3. Что такое хороший вопрос

Это один из главных критериев проекта.

Хороший вопрос должен быть:

* фактически корректным;
* основанным на документации;
* полезным для обучения;
* интересным;
* вовлекающим;
* требующим подумать;
* проверяющим понимание правила, а не механическое запоминание текста;
* практически применимым к работе картографа;
* однозначным с точки зрения правильных ответов.

По возможности предпочтительна структура:

```
ситуация → задача → варианты → решение
```

Например, вопрос может создавать небольшую рабочую ситуацию для картографа.

Но НЕ нужно искусственно превращать каждый вопрос в длинный сюжет.

Короткий вопрос допустим, если он действительно хорошо проверяет знание.

---

# 4. Что НЕ является целью

Не нужно:

* копировать длину 118 эталонных вопросов;
* копировать их формулировки;
* копировать их структуру;
* делать вопросы одинакового размера;
* искусственно усложнять вопросы;
* использовать сложные слова ради «умного» вида;
* создавать вопросы исключительно ради количества;
* генерировать выдуманные сущности;
* создавать десятки вопросов вокруг одного факта.

---

# 5. 118 существующих вопросов

В проекте существует набор из 118 хороших вопросов.

Они являются REFERENCE SET.

Используй их для понимания того, что считается хорошим квизовым вопросом.

Изучай в них:

* обучительную ценность;
* интересность;
* вовлечение;
* типы проверяемого мышления;
* качество вариантов ответа;
* практическую применимость;
* разнообразие;
* способы создания ситуации.

НЕ пытайся копировать:

* длину;
* количество слов;
* формулировки;
* шаблоны;
* поверхностный стиль.

Главный вопрос при анализе:

> Почему человек, который написал этот вопрос, решил, что его интересно и полезно решать?

---

# 6. Источник знаний

На первом этапе основной источник:

Яндекс.Справка NMaps.

В будущем система должна позволять подключать дополнительные сайты/источники с правилами.

Поэтому архитектура НЕ должна быть жёстко привязана к одному сайту.

Нужен абстрактный слой:

```
KnowledgeSource
```

с возможностью иметь:

```
YandexNMapsSource
OtherRulesSource
...
```

Источник должен сохранять связь:

```
знание → исходный документ → конкретный фрагмент
```

---

# 7. Источник истины

Критическое требование:

> Модель не имеет права считать собственные знания источником истины.

Источник истины — подключённая документация.

Если факт нельзя подтвердить источником, система должна считать его неподтверждённым.

Нельзя придумывать:

* правила;
* типы;
* сущности;
* допустимые значения;
* названия категорий;
* ограничения;
* свойства объектов.

---

# 8. Свобода генерации

При этом генератору НЕ нужно ограничиваться буквальным содержанием примеров из документации.

AI должен понимать смысл правила.

Например, если документация объясняет правила формирования названий, AI может самостоятельно придумать новое название и проверить картографа на этом новом примере.

То есть:

```
документация → смысл правила
```

а не:

```
документация → копирование примера
```

AI может свободно комбинировать подтверждённые знания и создавать новые ситуации.

Главное:

> Новая ситуация может быть придумана AI, но каждое используемое правило/факт должно быть подтверждено источником.

---

# 9. Онтология / Knowledge Model

Нужен отдельный слой структурированного знания.

Не обязательно строить сложную академическую OWL-онтологию.

Нужна практичная машиночитаемая модель предметной области.

Она должна постепенно извлекать из документации:

* сущности;
* типы сущностей;
* допустимые значения;
* свойства;
* связи;
* правила;
* ограничения;
* примеры;
* противоположности;
* иерархии;
* принадлежность к категориям.

Например условно:

```
Территория
    ├── тип
    ├── свойства
    └── правила

Ограничение
    ├── тип
    ├── область применения
    └── условия

Название объекта
    ├── структура
    ├── допустимые элементы
    └── ограничения
```

Это НЕ пример окончательной структуры.

Самостоятельно проанализируй документацию и предложи наиболее практичную модель.

---

# 10. Зачем нужна онтология

Она должна помогать генератору создавать корректные варианты ответа.

Например, если правильный ответ:

```
Тип территории X
```

неправильные варианты НЕ должны быть:

```
Тип территории Y
Тип территории Z
Выдуманная территория Q
```

если Y и Z не существуют.

Система должна уметь запросить:

```
valid_values(entity="тип территории")
```

и получить реальные значения из базы знаний.

Таким образом:

> AI не должен придумывать предметные сущности там, где существуют конечные справочные значения.

Это особенно важно для вариантов ответов.

---

# 11. Генерация вариантов

Количество вариантов:

```
2–6
```

Правильных ответов может быть:

```
1..N
```

Система должна явно хранить:

```
correct_answers[]
```

Нельзя предполагать, что правильный ответ всегда один.

Варианты должны быть:

* фактически допустимыми сущностями/значениями, если вопрос касается конечного справочника;
* либо логически правдоподобными вариантами, если вопрос проверяет применение правила.

---

# 12. Покрытие знаний

Ключевая проблема, которую необходимо решить:

> 15 вопросов не должны фактически проверять один и тот же факт 15 раз.

Перед генерацией пачки система должна определить, какие разные знания/аспекты выбранного раздела можно проверить.

Нужен этап:

```
Coverage Planning
```

Например:

```
раздел
  ↓
набор знаний
  ↓
потенциальные направления вопросов
  ↓
распределение N вопросов
```

Система должна стремиться к разнообразию:

* разных правил;
* разных сущностей;
* разных ситуаций;
* разных типов мышления;
* разных аспектов одного раздела.

Если в выбранном разделе объективно мало материала для N хороших вопросов, система НЕ должна искусственно создавать мусор.

---

# 13. Дубликаты

Нужно учитывать уже существующие вопросы.

Новый вопрос не должен быть:

* точным дублем;
* перефразированным дублем;
* вопросом с той же ситуацией и тем же знанием;
* бессмысленной вариацией существующего вопроса.

Проверка должна быть семантической, а не только по совпадению строк.

---

# 14. Самопроверка

После генерации должна существовать отдельная проверка.

Проверять минимум:

### Факты

Все утверждения подтверждаются источником.

### Ответы

Правильные ответы действительно правильные.

### Полнота

Если правильных ответов несколько, не пропущен ли ещё один.

### Однозначность

Нет ли ситуации, где два варианта можно разумно считать правильными.

### Квизовость

Интересен ли вопрос.

### Обучительность

Учит ли вопрос чему-то полезному.

### Практичность

Связан ли вопрос с реальной работой.

### Разнообразие

Не является ли он очередной вариацией предыдущего вопроса.

### Варианты

Не выдуманы ли сущности.

### Источник

Есть ли конкретное подтверждение.

---

# 15. Источник каждого вопроса

Каждый вопрос должен хранить:

```
source_document
source_section
source_fragment
source_reference
```

Желательно показывать куратору:

> Источник: [название раздела]
> [конкретный фрагмент/ссылка]

Куратор должен иметь возможность быстро открыть источник и проверить вопрос.

---

# 16. Автоматическое исправление

Если проверка обнаружила проблему:

```
generated
    ↓
validation
    ↓
problems
    ↓
targeted repair
    ↓
validation
```

НЕ перегенерировать всю пачку.

Если плохой только вопрос №7 — исправлять только №7.

Если проблема только в вариантах — не создавать заново весь вопрос.

Если вопрос невозможно исправить качественно — удалить его и при необходимости сгенерировать замену.

---

# 17. Ограничение времени

Критическое требование.

Предыдущая реализация могла работать около 120 минут ради примерно 15 вопросов.

Такого быть НЕ должно.

Целевой ориентир:

> 15–20 вопросов должны генерироваться за несколько минут, а не десятки/сотни минут.

Поставь архитектурный бюджет на:

* количество LLM-вызовов;
* параллельность;
* объём контекста;
* повторные проверки;
* retries;
* стоимость токенов;
* latency.

Не использовать последовательную цепочку из десятков вызовов без необходимости.

Предпочтительно:

* крупные batch-вызовы;
* параллельная обработка независимых задач;
* дешёвые детерминированные проверки обычным кодом;
* AI только там, где нужен reasoning.

---

# 18. Что НЕ должен делать LLM

Не отдавай LLM задачи, которые легко решаются обычным кодом.

Например:

* проверка JSON;
* количество вариантов;
* обязательные поля;
* duplicate по ID;
* сохранение;
* сортировка;
* фильтрация;
* техничесная валидация;
* подсчёты;
* управление состоянием;
* сравнение строк.

LLM используется для:

* понимания текста;
* извлечения смысла;
* планирования;
* генерации ситуаций;
* создания вопросов;
* reasoning;
* смысловой проверки.

# 20. Интеграция

Уже существует рабочий сайт-конструктор.

AI должен быть добавлен как отдельный модуль.

Не ломай существующий ручной ввод вопросов.

Должны существовать два независимых сценария:

```
Ручное создание
AI-генерация
```

Результат AI должен преобразовываться в тот же внутренний формат вопроса, который уже использует сайт.

---

# 21. UX

Куратор должен сделать минимум действий.

Основной сценарий:

```
Выбрать раздел
↓
Выбрать количество
↓
Сгенерировать
↓
Получить пачку
↓
Быстро просмотреть
↓
Выбрать нужные
↓

```

Для каждого вопроса:

```
вопрос
варианты
правильные ответы
источник
обоснование
действия:
    принять
    изменить
    удалить
    перегенерировать
```

---

# 22. Редактирование

Куратор должен иметь возможность сказать фактически:

> «Этот вопрос плохой — переделай».

Но система должна понимать контекст существующего вопроса.

При перегенерации необходимо:

* сохранить источник;
* сохранить тему;
* сохранить проверяемое знание, если оно хорошее;
* устранить конкретную проблему;
* не создавать случайно другой вопрос по другой теме.

---

# 23. Критерии качества

Создай внутреннюю систему оценки, но НЕ превращай её в бессмысленную сумму баллов.

Минимальные измерения:

```
factual_correctness
source_grounding
educational_value
engagement
practical_relevance
ambiguity
originality
coverage_diversity
answer_quality
```

Оценка должна помогать системе принимать решения:

```
accept
repair
reject
```

Не нужно показывать куратору внутреннюю «оценку AI», если это не приносит пользы.

---

# 24. Не надо бояться генерации

Пользователь прямо допускает ситуацию, когда AI предложит неидеальный вопрос, а куратор его удалит.

Поэтому система НЕ должна становиться настолько консервативной, что генерирует только банальные вопросы.

Нужен баланс:

```
factual safety
    +
creative freedom
```

Можно экспериментировать с формулировками и ситуациями.

Нельзя экспериментировать с фактами.

---

# 25. Расширяемость источников

Архитектура должна позволять в будущем подключить:

```
Яндекс.Справка
+ другой сайт с правилами
+ дополнительные документы
```

При этом источник каждого знания должен сохраняться.

Нельзя смешивать факты разных источников так, чтобы потом невозможно было понять происхождение утверждения.

---

# 26. Модель

Не привязывай архитектуру к одной LLM.

Нужен provider abstraction:

```
LLMProvider
```

Чтобы позже можно было менять:

```
MiMo
DeepSeek
Qwen
GLM
другую модель
```

без переписывания всей системы.

Отдельно предусмотрите возможность использовать разные модели для:

* генерации;
* проверки;
* дешёвых вспомогательных операций.

---

# 27. Производительность

Во время проектирования обязательно рассчитай:

* сколько LLM-вызовов нужно для 15 вопросов;
* какие вызовы можно выполнять параллельно;
* какие можно объединить;
* какой объём документации передаётся модели;
* где нужен RAG;
* где нужен cache;
* какие данные можно вычислить один раз;
* что можно сохранить между генерациями.

Сделай приблизительную оценку:

```
latency
token usage
стоимость
worst case
```

Цель — не просто «работает», а:

> работает быстро и предсказуемо.

---

# 28. Работа с ошибками

Предусмотреть:

* timeout;
* rate limit;
* невалидный JSON;
* пустой ответ модели;
* временную ошибку API;
* отсутствие источника;
* недостаток информации;
* невозможность создать нужное количество качественных вопросов.

Система не должна зависать на бесконечных retry.

---

# 29. Логи

Должно быть возможно понять:

* какие документы использовались;
* какие знания были извлечены;
* какой вопрос был сгенерирован;
* какие источники использовались;
* почему вопрос был отклонён;
* какие ошибки обнаружил validator;
* сколько занял каждый этап;
* сколько было LLM-вызовов.

Это необходимо для дальнейшего улучшения системы.

---

# 30. Тестирование

До запуска создать тестовый набор.

Использовать 118 существующих вопросов как reference/evaluation material.

Дополнительно создать набор тестовых случаев:

* один правильный ответ;
* несколько правильных;
* неоднозначный вопрос;
* вопрос с выдуманной сущностью;
* вопрос без подтверждения источником;
* два похожих вопроса;
* разные факты одного раздела;
* ситуация с несколькими связанными правилами.

Система должна проходить эти тесты автоматически.

---

# 31. Не начинай сразу писать код

Это обязательное требование.

Сначала:

### Этап 1 — аудит

# 32. Главный критерий успеха

Представь реального куратора.

Он хочет сделать новый квиз.

Ему не хочется:

* читать документацию часами;
* придумывать вопросы;
* придумывать варианты;
* проверять каждый факт вручную;
* искать источник;
* переписывать AI-текст.

Он хочет:

```
выбрать раздел
→
нажать кнопку
→
получить хорошие квизовые вопросы
→
быстро просмотреть
→
оставить хорошие
→
закончить квиз
```

Именно этот пользовательский сценарий является главным критерием продукта.

---

# 33. Принцип, который нельзя нарушать

Запомни:

> **Нам не нужно максимальное количество сгенерированных вопросов. Нам нужно максимальное количество качественных готовых квизовых вопросов на единицу времени куратора.**

Если из 20 генераций 15 хорошие — это успех.

Если из 100 генераций 80 хорошие, но система работает два часа — это плохой продукт.

Если AI создаёт абсолютно фактически корректные, но скучные вопросы — это тоже плохой продукт.

Нам нужны одновременно:

```
фактологическая надёжность
+
обучительность
+
вовлечение
+
разнообразие
+
скорость
```

# 34. Твоя задача как разработчика

Не воспринимай это ТЗ как приказ реализовать перечисленные технологии.

Если после анализа проекта ты считаешь, что:

* часть компонентов лишняя;
* RAG нужно реализовать иначе;
* онтологию лучше хранить иначе;
* некоторые AI-вызовы можно объединить;
* какая-то часть должна выполняться обычным кодом;
* существует более быстрый и надёжный pipeline;

— предложи изменение.

Но каждое существенное изменение объясни.

Главная цель — **рабочий, расширяемый, быстрый продукт**, а не соответствие этому документу любой ценой.
